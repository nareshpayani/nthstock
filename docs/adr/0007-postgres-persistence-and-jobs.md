# 0007. Postgres persistence and jobs

- Status: Accepted (owner, in the project chat, 2026-09-28)
- Date: 2026-09-28
- Spec: [`docs/specs/backend-core.md`](../specs/backend-core.md) (§3 to §9, §17, §18)
- Builds on: [0002](0002-core-stack.md) (core stack), [0004](0004-mock-backend-and-paper-engine.md)
  (mock backend and paper engine; its §3 said Postgres replaces the in-memory repos in Phase 3)

## Context

`apps/api` keeps every user, session, watchlist, paper order and ledger entry in memory behind one
`repo.ts` interface per module (ADR 0004 §3). Nothing survives a restart, the process is not
stateless as CLAUDE.md §4 requires, and the audit log, session list, TOTP, account deletion and the
scheduled market-session jobs have nowhere to live. CLAUDE.md D6 and §4 already name PostgreSQL 16,
Drizzle ORM, Redis 7 and BullMQ; this ADR records how they are used.

Constraints that shape the design:

- CLAUDE.md §4 plans PgBouncer in front of Postgres, so the app cannot rely on session state.
- Ticks are generated inside `apps/api` today (`ticks/tickPump.ts`), so every API process would run
  its own random walk and match resting orders against it.
- `packages/paperEngine` must stay pure (no Node-only imports, no I/O; ADR 0004 §2).
- Money is integer paise and times are stored in UTC (CLAUDE.md §6); PII is encrypted per column
  (CLAUDE.md §4 security baseline); the audit log is append-only (CLAUDE.md §4, §9).

## Decision

1. **Postgres is the record, Redis holds short-lived state.** PostgreSQL 16 through Drizzle ORM
   (`drizzle-orm/node-postgres`, driver `pg`) stores users, consents, devices, PINs, sessions,
   refresh tokens, TOTP factors, watchlists, paper accounts (orders, order events, ledger, positions,
   holdings, P&L snapshots) and the audit log. Redis 7 holds only what may be lost or rebuilt: OTP
   challenges and resend throttles, rate-limit counters, the session-revocation cache, pub/sub and the
   BullMQ queues. Database code lives in `apps/api/src/db/`; each module's Postgres repo sits next to
   its memory repo as `modules/<module>/pgRepo.ts`. No new workspace package.

2. **Two roles, migrations as the owner.** `nthstock_owner` owns the schema and runs migrations
   (`DATABASE_MIGRATION_URL`); `nthstock_app` is DML only (`DATABASE_URL`) and never runs DDL.
   `nthstock_purge` exists for the account purge job. Migrations are SQL files generated by
   drizzle-kit (plus hand-written ones for what Drizzle cannot express), committed and reviewed.
   `db:check` fails CI on drift between schema code and migrations. Production (Phase 6) migrates in
   a deploy step, never on app boot.

3. **The account store; the engine is a cache.** The per-user `PaperEngine` stays in the process and
   keeps being fed ticks, but its state is loaded from and committed to Postgres. `OrdersRepo` is
   replaced by an async account store: `load(userId)` returns a working-set snapshot and a
   `version`; `commit(userId, change, expectedVersion, auditEntries)` writes the diff, the audit
   entries and `version + 1` in one transaction, and fails with a conflict when the version moved.
   The caller reloads, re-applies once, then answers 409.

4. **Single writer (accepted simplification).** In this phase exactly one `apps/api` process runs
   the tick pump and matches resting orders. The version check makes any other writer (the job
   worker, or a second API instance serving requests) safe: it conflicts and reloads instead of
   corrupting an account. Moving matching into a dedicated worker fed by the Phase 4 quote service is
   Phase 4/5 work. The owner accepted this on 2026-09-28.

5. **Orders partitioned by IST trade date.** `orders` and `order_events` use declarative range
   partitions on `trade_date` (the NSE trading day in `Asia/Kolkata`; an AMO placed after the close
   belongs to the next session), one partition per day plus a `DEFAULT` partition. A daily job keeps
   14 days of partitions ahead. The partition key is part of the primary key, so nothing has a
   foreign key into `orders`.

6. **Column-level PII encryption.** Mobile, name, email and the TOTP secret are AES-256-GCM
   ciphertexts carrying a one-byte key id for rotation. Mobile lookups use an HMAC-SHA256 blind index
   with a separate key; `mobile_last4` backs the masked display. Keys come from `PII_ENC_KEYS` and
   `PII_HMAC_KEY` (`.env` locally, Secrets Manager in Phase 6); production refuses to start without
   them. Only `node:crypto` is used.

7. **Audit enforcement.** `audit_log` has no foreign keys (rows outlive a purged user and carry no
   PII). `nthstock_app` may only `INSERT` and `SELECT` it, and a `BEFORE UPDATE OR DELETE` trigger
   rejects changes for every role, the owner included. Order and fund entries are written in the same
   transaction as the change. `ledger_entries` gets the same grant treatment; only the purge role may
   delete a user's ledger rows, and no role may delete audit rows.

8. **Account deletion.** Soft delete at once (sessions revoked, `deleted_at`, `purge_after = now +
   ACCOUNT_PURGE_AFTER_DAYS`, default 30); the purge job then deletes the user's data and leaves a
   tombstone `users` row with no PII. Audit rows are kept without personal data. The owner approved
   this retention on 2026-09-28.

9. **PgBouncer-ready access.** One `pg.Pool` per process (`PG_POOL_MAX`, default 10). Only unnamed
   statements, no `LISTEN`/`NOTIFY`, no session advisory locks, no `SET` outside a transaction (only
   `SET LOCAL`, including the per-transaction `statement_timeout`), no temp tables. A test greps
   `apps/api/src` for the forbidden forms, and an optional compose profile runs PgBouncer in
   transaction mode locally.

10. **Storage driver switch.** `DB_DRIVER=memory|postgres` in `createDeps`: `memory` for unit tests,
    `postgres` for `npm run dev:api`, the Postgres scenario run and the api-mode E2E. Every Postgres
    repo passes the same conformance suite as its memory twin. `GET /v1/health/ready` reports
    Postgres and Redis and answers 503 when a configured one is down.

11. **Worker entry and `JOBS_MODE`.** The same codebase has a second entry, `src/worker.ts`
    (`npm run worker`), so jobs share repos and the paper engine. `JOBS_MODE=bullmq|inline|off`:
    `bullmq` schedules the market-session, P&L snapshot, partition, token cleanup and purge jobs on
    Redis with `tz: 'Asia/Kolkata'` cron and trading-day checks; `inline` keeps today's in-process
    sweep for tests that drive a manual clock; `off` for pure unit tests. Each job is a plain
    `run(at, deps)` function that is idempotent.

12. **Dependencies.** Named in CLAUDE.md §4: `drizzle-orm`, `drizzle-kit` (dev), `bullmq`,
    `testcontainers` (dev, already installed). New, approved by the owner on 2026-09-28: `pg` and
    `@types/pg` (dev) in `apps/api`, and `qrcode` (web, lazy-loaded) for TOTP enrolment. Versions are
    pinned exactly. Container images: `postgres:16-alpine` (compose, CI service, Testcontainers) and,
    for the optional pool profile, a pinned PgBouncer image. Not added: `@testcontainers/postgresql`,
    OTP, OpenAPI or encryption libraries.

## Consequences

- Restarting `apps/api` keeps every account; `npm run dev:api` needs Postgres as well as Redis
  (`npm run infra:up` starts both) and migrates before starting.
- Unit tests stay fast on the memory repos. Integration tests need Postgres: Testcontainers
  (`postgres:16-alpine`) by default, `POSTGRES_TEST_URL` to use a running server, and
  `SKIP_PG_INTEGRATION=1` (printed, shown as skipped) for machines without either. CI runs them
  against a Postgres service and never skips.
- A compromised app role cannot change the schema or rewrite the audit log.
- Horizontal scaling of order matching is not solved in this phase (decision 4); the version check
  keeps a second writer correct but not efficient.
- Old order partitions stay attached; detaching and archiving is a Phase 6 runbook.
- Losing the PII keys makes PII unreadable; production keys live in Secrets Manager (Phase 6).
